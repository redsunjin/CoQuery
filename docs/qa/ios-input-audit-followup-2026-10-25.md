# SQL·퍼즐 한글 입력과 접근성 경고 후속 확인

검증일: 2026-10-25. 기준 main: e22adedfba04c15a5f8c251469098c973a33f7ae (PR #28). iPhone 17e / iOS 27.0 Simulator / Xcode 27.1 / Capacitor Release WKWebView 앱을 사용했다. 이번 변경은 검증 문서만 추가하며 제품 코드·스타일·학습 판정을 바꾸지 않는다.

## 한글 조합 입력 직접 검증

문자열 주입 대신 iOS 화면 두벌식 키보드를 직접 눌렀다. 각 키 입력 뒤 키보드 후보·입력 화면을 관찰했다.

| 대상 | 절차 | 결과 |
| --- | --- | --- |
| SQL 편집기 | ㅎ→하→한→한ㄱ→한그→한글, 삭제로 한그, ㄹ 재입력, 공백으로 확정 | 정상. 조합 도중 글자가 사라지거나 중복되지 않음 |
| SQL 오류 경로 | 한글만 입력한 상태로 실행 | SELECT 문만 허용한다는 기존 오류를 표시하고 입력한 한글은 유지 |
| SQL 혼합 입력 | 화면 영문 키보드로 Select와 따옴표 입력, 두벌식으로 한글을 조합한 뒤 따옴표를 닫아 `Select '한글'` 실행 | 문장이 실행되고 학습 피드백·제출 SQL 기록에 한글이 유지됨. 요구한 주문 열과 다른 결과이므로 기존 판정은 오답. 정답 통과를 주장하지 않음 |
| C1 퍼즐 자기 설명 | 기존 `A matches both rules.` 앞에 동일한 한글 조합·받침 삭제·재입력·공백 확정 | `한글 A matches both rules.` 혼합 문장 정상 입력 |
| 설명 저장 | 설명 기록하기 선택 | 기록 완료 문구 표시 |
| 앱 재시작 후 설명 | 앱 종료·재실행→9개 퍼즐→C1→설명란 | 혼합 문장과 기록 완료 상태가 유지됨 |

SQL 편집기의 임시 작성 내용을 앱 재시작 뒤 복원하는 기능까지 통과했다고 해석하지 않는다. 이번 저장 확인은 SQL 제출 기록과 퍼즐 설명·기록 상태에 대한 것이다. 다른 조합 방식(천지인·외부 키보드), 긴 문장·1500자 경계·선택 영역 치환은 이번 범위에 포함하지 않았다. 영문 키보드의 자동 대문자화는 보였지만 SQL 실행에는 문제가 없었다.

## 접근성 경고 7건의 원인 확인

참여형 모의 체험의 질문 등록 화면을 Accessibility Inspector로 다시 검사하여 Hit Region 7건을 확인했다. 이전 검증과 같은 대상이며 경고가 사라졌다고 판단하지 않는다.

| 경고 대상 | 네이티브 Inspector가 보고한 크기(약) | 의미와 판단 |
| --- | --- | --- |
| SQL 학습 홈으로 | 86×16 | 실제 링크. CSS 상자와 접근성 보고 경계를 구분하여 추가 확인 |
| 참여형 검토 · 모의 체험 | 119×17 | p 요소인 정적 설명 문구. 버튼·링크가 아님 |
| 1. 질문 등록 | 55×16 | ol 안의 정적 li 단계 표시 |
| 2. AI 사전 검사 | 72×16 | 동일 |
| 3. 답변 | 34×16 | 동일 |
| 4. 요약 | 34×16 | 동일 |
| 5. 신고·항소 | 58×16 | 동일 |

정적 요소에는 클릭·키보드 활성화 동작이 없고 tabindex나 버튼 역할도 없다. 화면의 단계 표시를 누르면 해당 단계로 이동하는 탐색 버튼으로 해석해서는 안 된다. 경고를 줄이기 위해 정적 텍스트를 숨기거나 불필요한 버튼으로 바꾸지 않았다.

### 링크 실제 조작 영역과 글자 경계

1. 같은 CSS를 사용하는 로컬 웹 화면에서 읽기 전용 DOM 측정을 수행했다. 홈 링크의 실제 요소 상자는 약 100.36×44 CSS px, 텍스트 Range 경계는 약 100.36×18px였다. 정적 설명 문구의 텍스트 경계는 약 117.48×16px, 단계 문구는 약 55.31/71.28/33.94/33.89/57.42×15px였다. 단계 요소 자체의 높이는 36px였다.
2. 이 웹 측정은 데스크톱 브라우저에서 수행했으며, 네이티브 WKWebView의 정확한 접근성 프레임 측정과 동일하지 않다. 화면 크기·글꼴에 따른 차이가 있으므로 숫자를 혼합해서 네이티브 통과를 선언하지 않는다.
3. iOS 시뮬레이터의 Device Hub 화면에서 홈 링크 글자의 아래쪽 여백을 직접 눌렀다. 글자는 화면 y≈174, 터치는 y≈185였으며 SQL 학습 홈으로 정상 이동했다. 따라서 텍스트 줄 밖의 여백도 실제 터치 대상으로 동작한다는 증거를 확보했다. CSS의 최소 높이 44px 보완이 일반 터치에서 작동함을 뒷받침한다.

**추론:** Inspector의 WebAccessibilityObjectWrapper가 시각적 상자 전체보다 텍스트에 가까운 경계를 보고하여 경고에 영향을 주는 것으로 보인다. 정적 문구 6건의 숫자도 텍스트 경계와 유사하다. 다만 WebKit 내부 구현을 확인하거나 네이티브 접근성 프레임을 직접 읽어 원인을 확정한 것은 아니다. 이를 모두 거짓 경고라고 단정하지 않는다. 특히 일반 터치 성공이 VoiceOver 탐색 영역·낭독·활성화 전체를 보장하지 않는다.

## 변경 판단과 남은 확인

한글 입력 문제는 재현되지 않았고, 링크 여백 터치도 동작했다. 경고 수를 줄이기 위한 제품 수정은 하지 않았다. 7건은 위 근거와 함께 잔여 검토 대상으로 유지한다. 실제 기기에서 VoiceOver 링크 탐색·이중 탭, 포커스 영역, 낭독·로터·전체 흐름을 추가 확인해야 한다. 현재 단계 표시의 정적 의미 전달도 사용자와 검토해야 한다. 실제 사용자 검증은 수행하지 않았다.

검증 중 임시로 켠 Capture Keyboard는 off로 복원했고 화면 키보드는 닫았다. VoiceOver 설정은 변경하지 않았다. 실제 AI 요청 버튼을 누르거나 서버를 연결하지 않았다. 배포·앱스토어 제출은 하지 않았다.

## 검증 기록의 범위

네이티브 앱은 PR #28과 동일한 제품 자산으로 실행했다. 이번에는 문서만 추가하므로 새 제품 빌드를 만들 필요가 없었다. 이 문서의 한글 직접 입력·저장·재시작과 링크 여백 터치 확인은 새로 수행한 결과다. 기존 PR #28의 전체 회귀 검사 통과와 이번 직접 관찰을 구분한다. 이번 PR의 원격 검사·자동 리뷰 결과는 PR에서 확인할 수 있다.

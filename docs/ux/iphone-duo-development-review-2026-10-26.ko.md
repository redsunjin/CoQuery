# iPhone Duo 개발 방법·UI/UX 전용 검토

2026-10-26 KST. 대상: CoQuery의 Capacitor/WKWebView 앱과 공통 웹 학습 화면. **공식 자료 조사·코드 감사·개발 및 검증 기준을 포함한 검토이며, Duo 최적화 구현/시뮬레이터 실행/실기기 검증 완료가 아니다.** 배포·업로드·스토어 제출은 하지 않는다.

## 이전 검토 정정

앞선 넓은 화면 검토에서 iPhone Duo를 ‘미래 특정 모델’로 취급한 문구는 부정확했다. Apple의 [Duo 개발 안내](https://developer.apple.com/iphone-duo/)와 [전용 준비 지침](https://developer.apple.com/iphone-duo/prepare/)이 공개되어 있다. 일반 폴더블 대응을 참고 항목으로 두는 대신 **Duo를 독립적인 지원·검증 대상으로 포함한다**. 공개된 기기라는 사실과 CoQuery가 그 환경에서 검증되었다는 주장은 구분한다.

## 공식 지침과 CoQuery 적용 판단

|구분|공식 근거 요약|CoQuery에서 할 일(설계 판단)|
|---|---|---|
|빌드·크기 변화|SDK 버전에 따라 표시가 달라지며 iOS 27.1 SDK는 전체 표시와 세로 제어 영역에 대응한다. 화면 전체나 기기 방향 대신 현재 뷰·창 공간을 기준으로 삼고 크기 변화를 계속 처리한다. [준비 지침](https://developer.apple.com/iphone-duo/prepare/)|Xcode/SDK만 최신이라고 최적화 완료로 간주하지 않음. 네이티브 컨테이너와 웹 레이아웃을 함께 검사|
|접힌 화면·펼친 화면|하나의 작업과 기능 계층을 이어가며 큰 내부 화면에 여러 영역을 구성할 수 있다. 안전 영역과 시스템 제어 영역을 고려한다. [디자인 설명](https://developer.apple.com/videos/play/tech-talks/111466/)|접힌 화면은 집중할 작업 하나, 펼친 화면은 조작·근거 비교. 펼쳐야만 저장/도움을 쓸 수 있게 만들지 않음|
|접힘·가림 영역|네이티브 reserved region에는 구분 영역과 가림 영역이 있으며 활성 상태도 구분한다. 시스템 컨테이너의 적응도 활용할 수 있다. [적응형 레이아웃](https://developer.apple.com/videos/play/tech-talks/111463/)|중앙에 고정 폭의 빈 띠를 추정하지 않음. 실제 뷰 좌표의 영역을 확인해 조작을 피하도록 설계|
|측면 제어|네이티브 탐색 컨테이너와 바의 배치·축·우선순위를 점검해야 한다. 사용자 정의 제어는 별도 작업이 필요하다. [제어 영역 개발](https://developer.apple.com/videos/play/tech-talks/111462/)|HTML 헤더/버튼이 네이티브 바처럼 저절로 이동한다고 가정하지 않음. 기존 웹 조작과 네이티브 제어 역할을 명확히 분리|
|두 앱·복수 장면|다른 앱과 나란히 쓰는 것과 같은 앱의 여러 장면은 별개다. 공간·장면 변화와 새 장면 사용 가능성을 고려한다. [디스플레이·장면](https://developer.apple.com/videos/play/tech-talks/111464/)|우선 단일 장면에서 학습 연속성 확보. 복수 창·보조 화면을 지원 조건으로 무조건 추가하지 않음|

위 표의 오른쪽 열과 아래 배치는 CoQuery의 제안이며 Apple의 특정 구현 지시 또는 검증 결과가 아니다.

## 현재 코드·로컬 개발 환경에서 확인한 사실

- `xcodebuild -version`: Xcode 27.1, build 27A9275. iOS 및 Simulator SDK 27.1이 있다.
- CoreSimulator 조회: `iPhone Duo` 기기 유형(`com.apple.CoreSimulator.SimDeviceType.iPhone-Duo`)과 사용 가능한 iOS 27.1 런타임이 존재한다. 기기 유형의 최소 런타임은 27.1이다. 이번에는 Duo를 생성·부팅·설치·실행하지 않았다.
- `ios/App/App/AppDelegate.swift`의 SceneDelegate가 UIWindowScene을 사용한다. 별도 SceneDelegate.swift 파일이 있는 구조가 아니다. 조사한 앱 소스에 UIScreen.main 기반 크기 분기는 발견하지 않았다.
- Info.plist는 세로·가로 방향을 선언하고 `UIApplicationSupportsMultipleScenes=false`다. 이것만으로 다른 앱과의 나란히 사용을 막는다고 판단하지 않는다. 접기·펼치기 연속성을 별도로 확인해야 한다.
- 프런트는 HTML 사용자 정의 헤더·폼·버튼이다. CSS safe-area 변수는 있으나 적용은 주로 760px 이하 규칙에 집중되어 있다. 큰 내부 화면과 측면 시스템 영역까지 안전하게 반영하는지는 미확인이다.
- 탐구는 최대 920px, SQL 집중 화면은 최대 860px 한 열이다. 펼친 화면의 비교 작업을 위한 구성은 아직 없다. CSS viewport-segments 또는 네이티브 reserved-region 전달 구현도 확인되지 않았다.
- Apple 준비 지침의 resizability skill export를 시도했으나 Xcode 실행 단계에서 실패해 내보낸 스킬을 적용하지 못했다. 명령의 실패만으로 Xcode 설치가 손상됐다고 결론 내리지 않는다. 앞선 앱 컴파일 성공과도 구분한다.

## 개발 방식: 웹 작업 영역 + 필요한 네이티브 적응 계층

1. **공통 학습 상태 유지**: 같은 조건 계산·설명·창작 초안·저장본을 한 번만 보유한다. 접기/펼치기는 배치 변화이며 새 학습 시작이나 결과 제출이 아니다. 폼 복제와 웹뷰 재로딩으로 대응하지 않는다.
2. **공간을 계속 관찰**: 웹에서는 실제 컨테이너의 크기와 입력 가능한 높이를 기준으로 재배치한다. 기기명·화면 인치·고정 해상도로 분기하지 않는다. 네이티브에서는 현재 뷰/장면의 크기·안전 영역·가림/구분 영역을 확인한다.
3. **Duo 전달용 최소 검증 구현**: 네이티브 영역 정보가 WKWebView의 CSS에 자동 반영되는지 먼저 작은 검증 화면으로 관찰한다. 부족하면 Capacitor 플러그인/호스트에서 크기·안전 여백·예약 영역 변경을 공통 화면에 전달하는 적응 계층을 만든다. API 사용 가능 여부를 확인하고 이전 iOS에는 기존 화면으로 돌아가는 경로를 둔다. 이는 아직 미구현이다.
4. **좌표와 여백 계약**: 네이티브 뷰 좌표를 웹뷰의 실제 콘텐츠 좌표로 변환한다. 물리 픽셀·UIKit 포인트·CSS 픽셀을 같은 값으로 취급하지 않는다. 네이티브 여백과 CSS safe-area를 중복 적용하지 않는지 검사한다. 회전·줌·키보드·분할 창마다 갱신한다.
5. **제어 영역 선택**: 학습 폼과 데이터는 웹에 유지한다. 시스템 탐색·메뉴·확인 창의 네이티브 사용은 우선 검증하되, 웹 버튼에 네이티브의 자동 이동·접힘 회피가 적용된다고 간주하지 않는다. 화면 전체를 SwiftUI로 재작성하는 것을 선행 조건으로 삼지 않는다.
6. **장면 범위 통제**: 현재는 단일 장면의 지속성이 우선이다. 복수 장면·동시 외부 표시가 제품 목적에 필요한 경우에만 별도 상태 동기화·수명주기 설계를 한다. Info.plist의 복수 장면 스위치를 켜는 것으로 Duo 대응을 완료하지 않는다.
7. **일반 웹 대체 경로**: PWA는 네이티브 적응 계층 없이도 한 열·여러 영역으로 동작해야 한다. CSS Viewport Segments API는 기능 감지 후 활용 가능한 보조 경로이며, Duo 네이티브 앱의 대응을 그 지원 여부에만 의존시키지 않는다.

## Duo UI/UX 과업별 설계

|상태|탐구·창작·SQL 배치와 핵심 행동|
|---|---|
|접힌 외부 화면|하나의 작업과 짧은 단계 안내. 예상→실험→결과 왕복이 쉬워야 한다. 홈/다음/실행/저장을 측면 시스템 영역·카메라·키보드와 겹치지 않게 배치|
|펼친 내부 화면|넉넉한 공간에서는 왼쪽 문제·예상/규칙 편집, 오른쪽 결과·반례 근거/미리보기. 콘텐츠가 읽기 어려워지면 한 열 선택 제공. 실험 전에는 답을 노출하지 않음|
|부분 접힘·책처럼 사용|실제 활성 구분 영역을 확인해 주요 조작과 입력을 분리. 단순히 화면 중앙에 고정 간격을 만들지 않음|
|책상에 놓고 부분 접힘|근거·결과를 위쪽, 입력·주요 조작을 손이 닿는 아래쪽에 둘 수 있는지 검토. 다른 자세와 기능·이름·학습 순서는 동일|
|다른 앱과 나란히 사용|CoQuery 내부의 2열과 OS의 두 앱 나란히 사용을 구분. 좁아진 앱 창에는 2열을 강제하지 않음. 좌우 위치 변경 시 시스템 제어 영역과 폼 위치 재검사|
|입력·영상 등으로 높이 감소|설명·SQL 커서·한글 조합을 보존. 현재 입력을 가리지 않고 실행/저장으로 이동 가능하게 함. 배치 변경 때문에 선택 초점을 다른 곳으로 보내지 않음|
|펼친 상태에서 접고 다시 펼침|같은 문제·예상·설명·초안·저장본·결과 유효성 상태 유지. 접기만으로 서버 요청·SQL 실행·저장본 덮어쓰기·학습 완료가 발생하지 않음|

## 검증과 출시 관문

순서: 코드/계산 회귀 → 크기 변경 검증 화면 → **iPhone Duo 전용 시뮬레이터** → 실기기 → 실제 초보자 관찰. 브라우저 폭 변경과 기존 일반 iPhone 시뮬레이터 실행은 Duo 검증으로 환산하지 않는다.

필수 시나리오:

- 미실험/결과 확인/틀린 반례/자기 설명 작성/창작 수정/저장본 복원 각각에서 접기→펼치기→접기.
- 외부/내부 화면의 가로·세로, 부분 접힘, 다른 앱과 나란히 사용의 양쪽 위치, 키보드 표시/닫기, 작업 높이 감소.
- 한글 조합 중 전환, 커서/선택 범위, 큰 글자·확대·VoiceOver 읽기 순서·터치/포인터/외부 키보드.
- 시스템 측면 제어 영역, 안전 여백, 실제 구분/가림 영역과 실행·다음·저장·도움·확인 창의 겹침 확인.
- 앱 중단/복귀·오프라인 상태와 두 화면 전환. SQL 기록과 개념·창작 기록의 범위 및 지속성 확인.

통과 조건: 입력/선택/기록 손실과 무의도 실행·제출 0건, 필수 조작 가림 0건, 기능과 계층 동일, 이전 단계·결과·도움·저장본 복원 가능. 오류 수치만으로 사용성·학습 효과를 판정하지 않는다. 수행한 OS/SDK/커밋/자세/화면 상태와 증거를 남긴다.

현재 상태: 공식 지침 반영 및 로컬 도구/코드 조사 완료. 적응 계층·좌우 구성·Duo 시뮬레이터·실기기·사람 검증은 **미실시/미구현**. 스토어의 Duo 최적화 표기·스크린샷 제출·새 TestFlight 업로드는 이 검토에 포함하지 않는다.
